# Voice models for a directed, multi-character audiobook system

The strongest first experiment is **a prompt-based voice designer feeding a scene-capable speech model**, with a separate book director maintaining characters, relationships and narrative tension. For Inkwave, shortlist **MOSS-VoiceGenerator → MOSS-TTSD**, **VoxCPM2**, **Higgs TTS 2**, and **Qwen3-TTS VoiceDesign → Base**. Include Fish S2 Pro as a quality/scene reference if its license fits the intended use. These are audition priorities, not a verified sound-quality ranking.

**Rent a GPU for the first comparison; do not buy a 3090 yet.** The best scene model may need more than its 24 GB, and cheap fixed-voice TTS would not satisfy the character-performance requirement even if it ran quickly. Use the GTX 1070 for compatibility experiments and lighter stages; ordinary visitors need only a browser because completed narration is downloaded and cached.

The evidence does **not** establish a single open checkpoint that reliably analyses an entire novel, designs an Australian cast, accepts arbitrary private motive notes for every line, performs natural scene-level dialogue and preserves every word. Those are separate capabilities. The production system must connect them and verify their results.

## What the system should actually produce

A book is analysed before speech generation. The result is a persistent cast: each character's identity, personality, relationships, speech habits, textual evidence and an independently designed voice. A character's colour identifies the same person throughout the reader. Narration has its own actor and neutral presentation. Uncertain speaker assignments remain reviewable rather than becoming confident but wrong performances.

A chapter plan records the situation, emotional arc and transitions. A scene packet then contains the exact source dialogue, all participating speakers, preceding and upcoming exchange context, and non-spoken performance direction. Motive notes explain what the character wants or conceals; acoustic notes translate that into restraint, stress, tempo, hesitation or response timing. The persona guides performance rather than rewriting dialogue.

**Render an exchange or scene as a unit when the engine supports it.** Line-level annotations remain useful inside that scene. They should not force every line into a fresh, acoustically isolated request. A single whole-book request is also a poor first production unit: a late failure or one bad voice choice would be costly to repair. Scene boundaries offer manageable retries and corrections while preserving conversational interaction. A stateful turn-by-turn model carrying real preceding audio and text is also valid; the essential requirement is maintained context, not a rigid rule about request length.

After generation, align the audio to the original source, check speech fidelity and speaker identity, and store the accepted take. Character colour comes from source-span attribution; the moving playback highlight comes from verified timings. Colour can remain correct even when only passage-level timing is available. Whole-book direction, cast identity and delivery settings must be included in recording identity so an old take cannot silently masquerade as a newly directed one.

## Broad comparison

“Designed identity” means creating a new voice from a description without an existing voice recording. “Clone” means preserving an identity supplied by a reference clip, which may itself have been generated by a designer. “Scene” means the acoustic model receives multiple speaker turns together, not merely a script that calls a single-voice synthesizer repeatedly. Unverified is not the same as impossible.

## The candidates closest to the actual brief

### MOSS: voice design followed by jointly generated dialogue

VoiceGenerator accepts separate speech text and descriptive instructions, so a persona can become an auditioned reference. TTSD consumes speaker-tagged dialogue and the actors' references, providing an appropriate acoustic unit for exchanges. Its authors report up to five speakers and 60 minutes in one generation. That is a documented capacity, not a recommendation to start with hour-long jobs. [1][2]

A material limit remains: the shared processor has an instruction field, but the TTSD-specific examples do not establish that it follows arbitrary per-line motives or private scene-direction prose. The director should preserve those records and compile only supported controls. Passing unused metadata would provide the appearance of direction without its benefit. The ability to create a voice and the ability to vary that same voice under detailed acting instructions need separate listening tests. [2][3]

The current release table labels VoiceGenerator's backbone **1.7B**, not 8B. Repository metadata inspected during this assessment reports about 2.11B stored parameters and 4.23 GB of BF16 weights including its additional speech parameters. TTSD uses an 8B backbone, about 8.36B stored parameters and 16.71 GB of BF16 weights, before audio codec, activations and context cache. Load the designer and dialogue model sequentially. A conservative 48 GB first trial is an engineering allowance, not a measured minimum. [4][5][23][24]

The advertised MOSS “8 GB GPU” path refers to a specific quantized **MOSS-TTS** configuration with staged components and a 4,096-token context. It does not prove TTSD or VoiceGenerator running on a GTX 1070. Its TensorRT/FlashAttention choices also require hardware checks. The named MOSS weights and tokenizer declare Apache-2.0; runtime dependencies still have their own licenses. [6][25][26][27]

### VoxCPM2: designed voices with controllable cloning

VoxCPM2 materially strengthens the actor shortlist. Its official workflow supports creating a voice from a natural-language description, then preserving a reference timbre while changing delivery through parenthesized control text. The 2B backbone produces 48 kHz audio; the project and weights declare Apache-2.0. This closes an important documented gap in Qwen's design-to-Base workflow: identity reuse and delivery control are available together. [31][32]

The standard interface still takes one text and one reference, with optional prompt audio/transcript. No native cast list or arbitrary conversational-history interface was established. Treat it as a promising directed actor, not proof of a jointly performed scene. Its roughly 8 GB BF16 memory statement and 4090 speed results do not establish GTX 1070 support; Pascal needs a compatible dtype/runtime. Australian naturalness, retained identity during emotional changes, and whether subtle motive instructions translate convincingly all need an audition.

### Higgs TTS 2: described actors inside a scene

Higgs TTS 2 is unusually relevant because its model card documents speaker descriptions in a scene message, including multi-speaker output without reference audio. It also supports reference-conditioned identities. This is closer to the requested actor-and-scene interface than an emotion slider attached to independent lines. Its approximately 5.8B total parameters exceed the “3B” backbone label, and upstream recommends 24 GB GPU memory. [7][28]

The audition must test whether initial voices can be retained naturally across later scenes and whether motive/context notes improve restrained delivery. Its custom license has attribution, derivative and scale conditions. The newer Higgs TTS 3 is a separate candidate with different terms: its creator-content grant does not authorize public model hosting or product embedding. Newer is therefore not automatically the appropriate Inkwave release. [8]

### Qwen: an explicit design-and-reuse workflow, with a direction gap

Qwen documents creating a reference clip from a persona using 1.7B VoiceDesign, turning it into a reusable voice-clone prompt, and applying it to subsequent text through Base. This is a strong fit for constructing a stable cast. Its released models/tokenizer use Apache-2.0. A sequential 24 GB trial is a reasonable starting allowance. [9][10]

However, VoiceDesign, CustomVoice and Base are different interfaces. Base's cloning call does not expose the same separate delivery-instruction channel; CustomVoice provides instruction control over its preset voices. The documented clone workflow also does not establish one jointly generated multi-character exchange. Qwen could be the best **designer** while another model performs the scene. It should not be sold as the whole required pipeline before testing. [11]

### Fish, VibeVoice and the remaining alternatives

Fish S2 Pro deserves scene-level listening because it models multiple speakers and turns. Its public research license is a deployment constraint for a product demonstration, even if nobody pays to visit. Obtain a compatible grant if it wins rather than assuming a downloadable model permits every public use. The hosted S2.1 Pro name is not the same open checkpoint. [12]

VibeVoice's published long-form work addresses multi-speaker continuity, but the 1.5B release's four-speaker capacity and community-runtime situation need to be accounted for. A large novel can still have more characters by using only the active subset in each scene; a scene with narrator plus four characters already exceeds a four-speaker limit. This is an application boundary, not a reason to relabel or merge characters. [13]

Dia2 and CSM provide useful alternatives to purely stateless synthesis. Dia2 conditions English two-speaker dialogue with preceding audio prefixes; its documented scope is about two minutes. CSM generates a next turn from actual prior speaker/text/audio segments, with a finite context. Neither establishes prompt-designed personas or a full-book director. They should be tested as contextual exchange engines, not dismissed merely because generation can proceed one turn at a time. [33][34]

Index, CosyVoice and Chatterbox can be strong individual performers without providing native scene direction. They are useful controls in the audition and potential components, especially if a separate voice designer produces reusable identities. The CPU-oriented models matter when deployment simplicity or offline use wins. Pocket TTS and MOSS-TTS-Nano-100M have documented CPU-oriented paths, with native-runtime compatibility still needing verification on the actual host. [29][30] They should not set the quality ceiling for a server-rendered demonstration. The older/lighter baselines explain what is gained by the larger candidates; they are not recommendations to settle for robotic voices.

## How close are they to GPT Voice, ElevenLabs or Speechify?

There is no defensible universal percentage such as “95% as good as GPT voice.” Naturalness, accent, speaker identity, dialogue timing, emotional appropriateness and manuscript fidelity are different dimensions. A model can win a short-clip preference comparison and fail a chapter through drift, wrong speaker assignments or repeated words.

There is credible evidence that open models are competitive on some relevant tests. In the MOSS authors' dialogue evaluation, English speaker-attribution accuracy is about **96.3%** for their native TTSD setting. Their comparison with Eleven v3 shows mixed outcomes: the matched-voice TTSD row has stronger attribution/similarity, while Eleven's English word-error result is lower (**8.24% vs 10.05%** in that comparison). Those are developer-run dataset results, not error predictions for this novel, and ASR-based word error is not a direct human listening verdict. [14]

An independent provider-native-voice arena puts **Speechify Simba 3.2** ahead of **Eleven v3** and **Kokoro 82M** in its selected current table. That justifies an audition of Speechify's API rather than judging it by the consumer Free plan's robotic voices. The arena's US/UK voice filters and short-sample preference task do not establish Australian cast continuity, privately directed subtext, or a full audiobook. The [hosted review](READALONG-HOSTED-VOICE-RESEARCH.md) records exact scores, sample counts and intervals. [15]

“GPT voice” must also be separated into ChatGPT's conversational product, GPT-Live, Realtime and Mini TTS. The voice experienced in ChatGPT is not a promise about Mini TTS output. Mini TTS has a useful non-spoken instructions field but one voice per request; Realtime has conversational context but does not let an established session freely swap its voice after audio begins. Neither observation establishes a turnkey cast renderer. [16]

**Recommendation:** use Eleven v3 and the best suitable hosted voice as listening references, then choose the open system on the same original scenes. Compare both first takes and the best take after a fixed retry allowance. Otherwise the “best” model may simply be the one given twenty attempts.

## Direction and natural interaction

The director needs two records: a stable **voice/persona identity** and a changing **scene state**. A reserved character can become angry without suddenly acquiring a different timbre. A cheerful character can conceal bad news without a permanently “sad” voice. Persona analysis should cite the book; traits, relationships and accents absent from the text should be presented as casting choices, not recovered facts.

At line level, preserve the speaker, addressee, objective, subtext, emotional change and relation to adjacent turns. At scene level, record the shared situation, tension curve, pacing, interruptions and useful preceding acoustic context. The rendering adapter must explicitly state which fields its chosen engine can consume. Unsupported fields remain useful for review and candidate selection, but cannot be claimed as implemented control.

For a first experiment, use short coherent scenes with recurring actors and then a complete chapter. Increase duration only when the results survive a return-to-character test, scene-boundary test and transcript check. A model's advertised 60- or 90-minute context capacity is not evidence that a single maximum-length render is the best editorial workflow.

Keep the **spoken source** separate from the **director's material**. This is especially important where a model uses inline tags: encode only supported control syntax in a derived request representation and retain a mapping to the original text. Check that the generated recording does not read directions aloud, omit dialogue, invent words or move a sentence to the wrong actor.

The whole-book pass should be hierarchical on realistic hardware: examine every chapter, consolidate the cast and plot, resolve recurring names and aliases, then revisit scenes with the book-wide record available. That provides comprehensive source coverage without pretending an arbitrary-length novel and its generated audio can all reside in one small GPU context. Retain evidence links and uncertainty so an early summarization mistake does not become a permanent character fact.

## GPU rental versus buying hardware

These are **running compute-hour prices**, not finished narration-hour prices. The [GPU cost report](READALONG-GPU-OPTIONS.md) gives dated primary quotes, currency conversion, storage/idle charges and sensitivity calculations. A few current planning observations in Australian dollars:

| Runpod A5000 24 GB | 0.38 | Low-cost 24 GB audition candidate |
| Runpod RTX 3090 24 GB | 0.70 | Useful same-card comparison with ownership |
| Runpod RTX 4090 24 GB | 1.04 | Faster candidate; cost per accepted scene still needs measurement |
| Vast RTX A6000 48 GB, specific observed offer with 30 GB disk | 0.67 | Conservative larger-model audition candidate |
| Runpod A6000 48 GB | 0.74 | Larger memory margin for the first TTSD trial |

For example, **four billable A6000 hours at approximately A$0.74 cost about A$2.97 in compute**, before storage, transfer and taxes. This is an audition-session illustration, not a promise to render a whole book in four hours. Conversely, leaving a GPU billed continuously converts a cheap hourly quote into a recurring monthly bill; scale-to-zero or deliberate shutdown matters for a lightly used demo. [17]

A 3090's 24 GB is a useful capacity class, but not a reason to buy before selecting the engine. Current direct seller asking prices found in the cost review are roughly A$2,250; they are neither completed-sale values nor a reliable market median. Use the actual card quote in the break-even formula:

`purchase cost / (cloud cost per comparable GPU hour − local electricity cost per busy hour)`

Include the computer's extra hardware requirements, reliability, maintenance and eventual resale value when deciding, and compare **equal accepted output**, not just equal hours on different GPUs. At the assumed A$0.30/kWh and 350–500 W system load, local electricity is about A$0.105–0.15 per busy hour. Lower card prices improve ownership economics, while a very cheap rental can leave little saving per owned hour. For a demonstration with low traffic, rental avoids paying up front for the wrong VRAM class. [17]

## API cost perspective

For **100,000 words ≈ 600,000 characters**, current ElevenAPI v3/Multilingual-v2 usage is about **US$60** before retakes and other charges. The current Speechify API Starter price is **US$10/month including 1.9 million characters**, so that allowance covers the assumed book. This API is different from consumer Speechify Free; its contractual restrictions still matter for a public voice product. OpenAI's older TTS-1/HD character rates imply US$9/18 for this text, but those are different models. Mini TTS bills input text and output audio tokens separately, so use measured usage for a reliable book quote. [18][19][20][21][22]

Cheap rental is not automatically the cheapest total product path. A director, speech model, alignment pass, failed takes, idle time and retained audio all contribute. Conversely, self-hosting gives access to models and casting workflows that a cheaper single-voice API may not provide. For Inkwave, the reason to choose a self-hosted scene system is the combined **quality, control and economics**, rather than assuming every hosted product costs Eleven's rate.

## Deployment: Vercel and the Windows worker

Keep the public website on Vercel. Give it a durable job service for submission, status and accepted output; use persistent object storage for files. The Windows desktop initiates an outbound HTTPS connection to claim work. It does not need a connection to the Mac, a public home IP, or router port forwarding. An eventual cloud worker can implement the same protocol.

A modest demonstration can process one production job at a time. Save the plan, approved character references and completed scenes durably, so a driver failure or desktop reboot resumes from a checkpoint. Vercel functions coordinate short requests; the GPU process owns long inference. No browser should wait on a many-hour serverless invocation. Each book gets a private, unguessable job receipt even when visitors need no paid account.

A cast review should precede the first whole-book render. Show each character's profile, voice audition and dialogue colour; allow correction of attribution or casting. The permanent character colour identifies who speaks, while the moving media-clock highlight identifies the current words. Persist voice/model/direction versions with each take. An uncertain alignment gets an explicit passage fallback, not invented word timestamps.

The [Windows preparation script](../scripts/windows/Prepare-InkwaveNarrator.ps1) and [instructions](../scripts/windows/README.md) inspect the host and can prepare an isolated Pascal-compatible CUDA runtime. They are **not an already-connected Vercel worker**. This session cannot reach the Windows desktop, and the connected Vercel account currently exposes no teams. Public queue deployment and the production GPU pipeline therefore remain pending. No cloud rental or GPU purchase has been made.

## Acceptance test before choosing a model

1. Use the same original scenes: restrained domestic dialogue, concealed disagreement, a brief interruption, a serious emotional turn, and a character returning later. Include a narrator and two characters initially, then test the model's speaker limit.
2. Design genuinely distinct Australian identities from the same descriptions. Keep one approved voice per character across all scenes; record references, prompts, seeds and model revisions.
3. Compare a context-free rendering with the proposed scene-directed rendering. This tests whether direction actually helps rather than merely making the output more emphatic.
4. Listen blind and level-matched. Score authenticity, vocal consistency, response timing, subtext, restraint and listening fatigue. Keep literal reading accuracy and speaker attribution as separate checks.
5. Count first-take success, retakes, omitted/repeated words, peak VRAM/RAM, wall time and total bill. Measure **cost per accepted minute**, not the fastest cherry-picked clip.
6. Only after the short scenes pass, render a chapter and then a book. Whole-book quality, Australian authenticity and natural actor interaction remain empirical requirements.

No number in an unrelated leaderboard substitutes for this test. If none of the open models clears the listening bar, the honest result is to revisit the model or the product scope, rather than present an inexpensive monotone as a completed cinematic reading system.

## Current implementation checkpoint

EPUB/PDF import and the existing reader/audio library work locally. A CPU Kokoro proof also runs with no provider key; it is explicitly a baseline. On the Intel i9 Mac, using two inference threads, three synthetic 16–17.5-second samples took about 27–29 seconds each and reached approximately 624–774 MiB peak process RSS. Those small measurements demonstrate feasibility, not an average-machine benchmark or quality parity with the shortlisted models.

The local code passed TypeScript, production build, **72 isolated reader tests**, and the Chromium/WebKit import, audio and local/paid-engine regression suites. The Windows GPU runtime, book director, designed cast, character-colour interface, durable Vercel queue and best-model deployment have **not** been validated or shipped by this checkpoint. These proposed features should not be inferred from the working baseline's “render book” button.
